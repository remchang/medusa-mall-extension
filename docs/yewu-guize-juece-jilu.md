# 业务规则决策记录：收藏夹（shoucang）

> 实验 02 自主开发功能 · 一页决策记录

## 1. 功能选择与用户价值

**选择的功能**：登录用户的商品收藏夹，并支持跨设备同步。

**用户价值**：在线商城的商品往往需要反复比较。用户在浏览时看到感兴趣的商品，
但当下不打算买，就需要一个「先存着」的地方。如果只能靠浏览器书签，换设备后就找不到了。

**验收条件**（建 Issue 时先写好，实现后逐条核对）：

| 编号 | 验收条件 | 核对结果 |
|---|---|---|
| AC-1 | 登录用户可以在商品详情页收藏商品 | ✅ 通过 |
| AC-2 | 换一个浏览器登录同一账号，收藏夹内容一致 | ✅ 通过（数据存在 PostgreSQL，不依赖本地存储） |
| AC-3 | 同一商品重复收藏不会产生两条记录 | ✅ 通过（幂等，返回 `yiyoucunzai: true`） |
| AC-4 | 可以取消收藏，且不能取消别人的收藏 | ✅ 通过（403 越权拦截） |
| AC-5 | 商品下架后收藏记录保留，界面明确标注 | ✅ 通过（`is_active: false`，灰显 + 标签） |

## 2. 数据归属

**决策**：收藏数据归 **客户（customer）** 边界，独立成一个自定义 Module
`shoucang`，表 `shoucang_item`。

**为什么不放在商品模块**：收藏是「人对商品的关系」，一条收藏记录的存在与否
取决于人，而不是取决于商品。如果把收藏挂在商品上，删除商品就得连带处理所有收藏。

**为什么不放在购物车模块**：购物车是「本次结账的意图」，清空购物车是常规操作；
而收藏是「长期兴趣」，不应该被清空购物车影响。

**为什么不放在订单模块**：订单是交易记录，只有成交才有订单；
而收藏发生在浏览阶段，早于任何交易。

## 3. 数据模型

表 `shoucang_item`：

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | text PK | 主键 |
| `kehu_id` | text | 归属客户 ID |
| `shangpin_id` | text | 收藏的商品 ID |
| `beizhu` | text nullable | 客户自写的备注，如「等降价」 |
| `created_at` / `updated_at` | timestamp | 框架自动维护 |

**为什么不存商品价格和标题的快照**：
商品价格由商品模块持有。如果收藏表也存一份价格，商品改价后收藏页就会显示旧价格，
产生数据不一致。因此收藏表只存「谁收藏了什么」，价格在查询时联商品表实时取。

## 4. 接口设计

| 方法 | 路径 | 说明 | 主要状态码 |
|---|---|---|---|
| POST | `/store/shoucang` | 收藏商品 | 201 新建；200 已存在；400 参数错；401 未登录 |
| GET | `/store/shoucang` | 查询收藏夹 | 200；401 未登录 |
| DELETE | `/store/shoucang/:id` | 取消收藏 | 200；401；403 越权；404 不存在 |

**为什么不用 Medusa 上游的 Store API**：
上游没有收藏概念。这里使用 Medusa 提供的 **自定义 API 路由**扩展点
（`src/api/store/`），不修改框架和 node_modules。

## 5. 故障状态处理

| 场景 | 后端行为 | 前端行为 |
|---|---|---|
| 匿名用户点收藏 | 401 `not_allowed` | 不发请求，直接提示「请先登录」 |
| 重复收藏 | 判断已存在，返回 200 + `yiyoucunzai: true`，**不新增记录** | 提示「该商品已在收藏夹中」，不误报「收藏成功」 |
| 收藏不存在的商品 | 校验商品表，400 `invalid_data` | 显示后端返回的中文提示 |
| 取消他人的收藏 | 比对 `kehu_id`，403 `forbidden` | 显示「无权操作他人的收藏记录」 |
| 重复点「取消收藏」 | 第二次查到记录不存在，404 `not_found` | 显示「该收藏记录不存在」，不假装成功 |
| 商品下架 | 记录保留，返回 `is_active: false` | 灰显卡片 + 「已下架 · 暂时无法购买」 |
| 商品被删除 | 返回 `deleted: true`，`shangpin` 为 null | 显示「该商品已下架或被删除」，仍可移除 |

## 6. 权限

- 三个接口全部要求登录（通过 `req.auth_context.actor_id` 取得客户身份）。
- **越权防护**：删除时不仅按收藏记录 ID 查，还额外比对 `kehu_id`。
  只按 ID 删除是典型的越权漏洞——拿到别人的记录 ID 就能删别人的数据。
- 自定义模块的 Service 只在服务端被调用，不向外暴露。

## 7. 与商品下架 / 库存变化的关系

- **商品下架**：收藏记录不动。用户仍能看到自己收藏过什么，只是标注不可购买。
  如果下架就自动删收藏，用户会莫名其妙地发现收藏变少。
- **库存变化**：收藏**不预占库存**。
  这是刻意的设计取舍——如果收藏就锁库存，一个用户把热门商品全收藏就能把库存锁死，
  构成拒绝服务。库存的预占发生在加入购物车之后。

## 8. 重复请求与并发

- 收藏接口的幂等判断是「查一次，没有再插」。
  在高并发下两个请求可能同时通过检查，理论上会产生两条记录。
  当前实现用 `chaxun_shifou_yishoucang` 覆盖了常规的重复点击场景（这是本实验的测试重点）。
  更严格的方案是给 `(kehu_id, shangpin_id)` 加唯一索引，让数据库兜底——
  这一点在报告的「未解决风险」里如实说明。

## 9. 测试要点

- `integration-tests/http/shoucang.spec.ts` 覆盖：未登录 401、正常收藏 201、
  重复收藏不新增、取消收藏 200、越权 403、不存在 404、空收藏夹返回空数组。
